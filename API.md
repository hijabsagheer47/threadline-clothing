# Fashlab Studio — Customer API (v1)

REST API for the Flutter mobile app. Customer side only — nothing here touches
the admin panel.

**There are no customer accounts.** The app mirrors the website: a visitor
browses, fills in the checkout form and orders as a guest. No registration, no
sign-in, no order history. The only login anywhere is the admin panel on the
website, which this API does not expose.

**Interactive docs (live):** <https://fashlabstudio.mytechrcm.com/api/docs.html>
Swagger UI over the live API. Click **“Get a device token & authorize me”**
once, then run any endpoint from the browser with *Try it out*.

**Base URL:** `https://fashlabstudio.mytechrcm.com/api/v1/index.php`

> This webspace applies mod_rewrite *patterns* but silently drops the
> *substitution* — which is why the storefront's pretty permalinks
> (`/product/{slug}`) 404 there and it serves `/product.php?slug=…` instead.
> The API therefore routes on `PATH_INFO`, not on a rewrite:
>
> | Form | URL |
> |---|---|
> | PATH_INFO (**use this**) | `…/api/v1/index.php/products?per_page=20` |
> | Query string | `…/api/v1/index.php?_route=products&per_page=20` |
> | Clean (only where rewrites work) | `…/api/v1/products?per_page=20` |

## 1a. Postman

`Fashlab-API.postman_collection.json` — import it into Postman
(**Import → File**) and everything is set up:

- **Bearer auth** is on the collection, reading a `token` variable.
- Run **Session → Get a device token** once; its response fills `token`, and
  every other request picks it up.
- Requests chain: listing products, categories, collections, pages or the
  journal fills that list's own slug variable; adding to the cart fills
  `cartKey`; placing an order fills `orderNumber`. The variables also ship with
  working defaults, so any request answers on the first send.
- Folders are ordered to be runnable top to bottom — **Run folder** on *Cart*
  adds an item, reads it, updates it, then clears it.
- Optional query filters ship **disabled**; tick them in the Params tab.

The coupon example uses `WELCOME10`, which is a placeholder — replace it with a
code from **Admin → Coupons**.

The OpenAPI 3 spec is served at `/api/v1/openapi.json` — import that instead if
you prefer, or feed it to a Dart client generator.

Both files are generated by `scripts/build-api-docs.py`, which fails if either
drifts from the routes in `api/v1/routes/`:

```bash
python3 scripts/build-api-docs.py
```

## 2. Every response has the same shape

```json
{
  "success": true,
  "message": "Saved to your wishlist.",
  "data":    { },
  "errors":  { }
}
```

- `success` — always present. Branch on this, not on the HTTP status.
- `message` — safe to show to the customer as-is.
- `data`    — the payload; `null` on failure.
- `errors`  — `{ "field": "message" }` on a 422, so it maps straight onto
  Flutter form validators.

**Status codes:** `200` ok · `201` created · `404` not found · `405` wrong
method · `422` validation · `503` store closed / API not installed.

Paginated endpoints wrap their list:

```json
{ "items": [ ], "meta": { "page": 1, "per_page": 20, "total": 120, "pages": 6, "has_more": true } }
```

## 3. The device token

Every request carries a token:

```
Authorization: Bearer <token>
```

**This is not a login.** It is an anonymous device identity that holds the cart
and the wishlist, because a phone has no session cookie. It grants no access to
anyone's data.

### First launch

```
POST /session      { "platform": "android", "device_name": "Pixel 8" }
→ data: { token, is_new, cart_count, wishlist_count }
```

Store `token` in secure storage and send it on every request afterwards. Safe
to call on every launch: with a valid token it returns that same token rather
than starting a new cart.

If a request arrives with a missing, unknown or expired token, the API issues a
fresh one instead of failing, and returns it in the **`X-Api-Token`** response
header. Read that header on every response and replace your stored token when
it differs.

Tokens last 180 days and the clock resets on each request.

| Method | Endpoint | Notes |
|---|---|---|
| POST | `/session` | Issue / confirm the device token |
| GET  | `/health` | Connectivity check |

## 4. Catalogue

| GET | `/home` | **One call for the whole home screen** — hero, categories, collections, featured / new / best sellers / on sale, testimonials |
| GET | `/products` | See filters below |

### `/products` query parameters

| Param | Values |
|---|---|
| `q` | free text |
| `category` | slug or id |
| `collection` | slug or id |
| `sort` | `newest` `featured` `best_selling` `price_low` `price_high` `name` |
| `price` | `under-5000` `5000-10000` `10000-15000` `over-15000` |
| `price_min` / `price_max` | numbers (ignored when `price` is set) |
| `fabric` / `color` / `size` | facet values from `/filters` |
| `availability` | any value = in stock only |
| `sale` | any value = on sale only |
| `featured` | any value = featured only |
| `page` / `per_page` | `per_page` max 48, default 20 |

Every product carries display-ready fields so the app does no price maths:

```json
{
  "id": 92, "name": "...", "slug": "...",
  "price": 6875, "sale_price": 6050, "final_price": 6050,
  "on_sale": true, "discount_percent": 12,
  "formatted_price": "Rs. 6,050", "formatted_compare_at": "Rs. 6,875",
  "in_stock": true, "stock_quantity": 10,
  "rating": 4.5, "rating_count": 12,
  "badges": [ { "label": "SALE", "type": "sale" } ],
  "image": "https://fashlabstudio.mytechrcm.com/images/products/x.jpg"
}
```

Image URLs are always absolute. Product detail adds `images[]`,
`variant_groups[]` (options grouped by "Size", "Colour", …), `categories[]`,
`description`, `care_instructions` and `share_url`.

## 5. Cart

Every cart call returns the **complete cart**, so you never need a follow-up
`GET`.

| Method | Endpoint | Body |
|---|---|---|
| GET | `/cart` | — |
| GET | `/cart/count` | — (cheap badge refresh) |
| POST | `/cart/items` | `product_id, variant_id?, quantity?` |
| PATCH | `/cart/items` | `key, quantity` — **preferred** |
| PATCH | `/cart/items/{key}` | `quantity` |
| POST | `/cart/items/remove` | `key` — **preferred** |
| DELETE | `/cart/items/{key}` | — |
| DELETE | `/cart` | Empties the cart and drops the coupon |
| POST | `/cart/coupon` | `code` |
| DELETE | `/cart/coupon` | — |

A cart key looks like `92:0` (`product:variant`). The colon is legal in a URL
path but some HTTP clients and proxies mangle it, so **prefer the body forms**;
percent-encode the key (`92%3A0`) if you use the path form.

Prices, stock and coupon validity are recalculated on the server every time.
Anything the client sends about money is ignored.

## 7. Checkout and orders

| Method | Endpoint | Body |
|---|---|---|
| GET | `/checkout` | Cart, delivery options, payment methods |
| POST | `/orders` | The checkout form — see below |
| POST | `/orders/track` | `order_number, contact` |
| GET | `/orders/{order_number}?contact=…` | Same lookup, for deep links |

### Placing an order

```json
POST /orders
{
  "name": "Ayesha Khan",
  "email": "ayesha@example.com",
  "phone": "03001234567",
  "address": "House 12, Street 4, DHA Phase 5",
  "city": "Karachi",
  "postal_code": "75500",
  "delivery": "standard",
  "notes": "Please call before delivery"
}
```

`delivery` is `standard` or `express` (express adds a flat fee).
**Payment is Cash on Delivery only** — no gateway is connected, so accepting a
card would create an order the store could never settle.

### Getting back to an order

With no account, the **order number plus the email or phone used on it** is the
only way back — the same rule as the site's track-order page. Requiring the
contact is what stops an order number on its own from exposing someone's
address.

**Keep `order_number` from the response** and show it on the confirmation
screen.

Orders are created by the same server-side function the website checkout uses,
so stock, coupons and the inventory log can never drift between the two.

## 9. Flutter notes

**Screen → call**

| Screen | Call |
|---|---|
| Splash | `POST /session`, then `GET /settings` |
| Home | `GET /home` |
| Shop / search results | `GET /products?…` |
| Filter sheet | `GET /filters` |
| Product | `GET /products/{slug}` |
| Cart | `GET /cart` |
| Checkout | `GET /checkout` → `POST /orders` |
| Order confirmation | the `order` in the `POST /orders` response |
| Track order | `POST /orders/track` |

**Interceptor checklist**

1. Attach `Authorization: Bearer <token>` to every request.
2. After each response, if `X-Api-Token` differs from your stored token, save
   the new one.
3. On `503`, show a "store is closed" screen.
4. Read `success` first; show `message` on failure; map `errors` onto form
   fields on a `422`.

Send bodies as JSON (`Content-Type: application/json`); form-encoded works too.

**No CSRF token is needed.** The website's `/api/cart.php` and
`/api/wishlist.php` still require one — those are for the browser and are
unchanged. The app should use `/api/v1/*` only.

**New**

```

includes/api-auth.php          device tokens + cart/wishlist state
includes/order-service.php     shared order placement
api/v1/index.php               router

api/v1/helpers.php             response envelope + JSON transformers

api/v1/openapi.json            generated OpenAPI spec
Fashlab-API.postman_collection.json   generated Postman collection
api/docs.html                  Swagger UI
scripts/build-api-docs.py      regenerates and verifies both
```

**Modified**

| File | Change |
|---|---|
| `.htaccess` | Route `/api/v1/*` to the front controller; `AcceptPathInfo On`; preserve `Authorization` on PHP-CGI |
| `includes/bootstrap.php` | Load the new files; exempt `/api/` from the HTML maintenance page |
| `checkout.php` | Order placement moved into `includes/order-service.php` — same behaviour, now shared with the API, and wrapped in a transaction so a mid-write failure can no longer leave a half-created order |

Nothing else on the website changed. Templates, styling, the admin panel and
all existing data are untouched.
